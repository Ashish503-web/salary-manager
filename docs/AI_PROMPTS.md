# AI tooling log

This project was built with Claude Code (Anthropic's agentic CLI). This doc records how AI was used, not just that it was used, since the assessment specifically asks us to show our thinking.

## Process

1. **Requirements clarification before any code.** Given the raw assessment brief, the first step was resolving the ambiguities it deliberately left open: exact backend framework (Express + TypeScript + Prisma + SQLite), frontend tooling (Vite + React + shadcn/ui + Tailwind), and deployment approach (local run + documentation instead of a hosted deploy, given no infra accounts were pre-set-up for this exercise). These were asked as explicit multiple-choice questions rather than assumed, since they're product/engineering decisions the requester should be able to steer.

2. **Plan-mode design pass before writing files.** Before touching the filesystem, a full implementation plan was drafted and approved: data model (`Employee`/`SalaryRecord`/`User`), the "salary as history not a field" decision, the full API surface, the seed script's approach to generating realistic 10,000-row data, the commit sequence, and the doc set. This plan is preserved as the basis for `docs/ARCHITECTURE.md`. The goal of doing this up front was to make the *design* decisions — not just the code — visible and reviewable before implementation time was spent.

3. **Parallel delegation with a fixed contract.** The backend (`server/`) and frontend (`client/`) were implemented by two agent instances working in parallel on disjoint directories, each given the *same* API contract (endpoint shapes, request/response fields, auth header, error format) so they'd compose correctly without needing to coordinate with each other mid-build. Each agent was instructed to: build to the contract, write and pass its own unit/integration tests, run its own seed/build/test commands, and report deviations rather than silently improvising around gaps in the spec. This is the same reason the requirements doc calls out what's *excluded* — a clear contract (what's in, what's out, what shape) is what let two independent build processes converge on a working system instead of two half-compatible ones.

4. **Docs written directly, not delegated.** `docs/REQUIREMENTS.md`, `docs/ARCHITECTURE.md`, and this file were written directly rather than generated by a sub-agent, since they're meant to represent the actual reasoning behind the build, not a description reconstructed after the fact.

5. **Review pass.** After both build agents reported back, their output was reviewed (build/test output, spot-checking key files, running the seed script and both test suites) before the code was committed. Any correctness or scope issues found here were fixed directly rather than re-delegated, and are visible as their own commits.

6. **Follow-up verification and optimization pass.** In a later session, before committing the (still-uncommitted) build, everything was re-verified from scratch: `npm run seed` re-run to confirm 10,000 employees generate deterministically, both test suites re-run, both apps type-checked and built, and the live server exercised with real HTTP requests (login, paginated employee list, all analytics endpoints) rather than trusting prior agent reports. This surfaced two concrete improvements, applied directly: the `/analytics/recent-changes` endpoint issued one extra DB round-trip per row to find each employee's previous salary — replaced with a single batched `employeeId IN (...)` query so the endpoint's query count no longer scales with the requested row count; and the client's production bundle triggered Vite's 500KB chunk-size warning because `recharts` shipped in the same chunk as app code — fixed with explicit `manualChunks` (react/router, recharts, form libraries split out), which also improves browser cache reuse across deploys since vendor code changes far less often than app code.

## Where AI judgment mattered most

- Choosing to model salary as a `SalaryRecord` history rather than a mutable field on `Employee` — this wasn't in the brief, but follows directly from "audit trail" and "recent changes" being implied needs of an HR manager who has to explain compensation decisions.
- Deciding what to explicitly leave out (chatbot Q&A, live FX, RBAC, bulk import) and writing down *why*, per the assessment's own request for that reasoning — treating scope-cutting as a design decision, not a shortcut.
- Keeping country/department/level as static config instead of DB tables — a deliberate "don't build CRUD nobody asked for" call, documented in ARCHITECTURE.md as the first thing to revisit if requirements change.
